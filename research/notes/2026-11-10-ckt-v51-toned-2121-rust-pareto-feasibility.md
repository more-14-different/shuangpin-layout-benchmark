# 带调 21×21 少量声介例外的 Rust Pareto 可行性审计

日期：2026-11-10

## 结论

可以扩展现有 Rust core，而且值得做；不需要另写求分内核，也不应把旧生产分支的搜索器整块移植过来。

当前方向固定为：

- 拼读 11 韵；
- 三横 `7:7:7` 调区；
- 固定词辅策略 `12/213/24`；
- 暂不比较 120 种形笔语义排列、144 套词辅和五辅自身映射序；
- 只给声介侧少量、可解释的例外，把预算用于 `CKT v5.1 / M / D / F` Pareto。

已有 Rust 的碰撞消解、运动代价、增量回滚、前沿和检查点设施都可复用。真正缺少的是两层薄适配：带调二键码状态，以及完全等价于 JS CKT v5.1 的词条模板。本轮已经完成第一层的最小实现和回归验证；第二层仍须完成后，才能声称 Rust 数值与 JS 完全同口径。

## 各分支的 Rust 资产

审计了所有远端分支中未进入当前分支的 Rust 提交。结论是它们共享同一个 `NativeCorpus + IncrementalResolver` 内核，长期任务的差别主要在候选生成和硬约束，而不是另一套更快的求分器。

最有用的资产有两类：

1. `origin/production/ckt-v4-2121-strict-avuio-20261024`
   - `9d9836b`、`0864d60`：严格 21×21 / AVUIO 守卫和长期流水线；
   - `11713b6`：`search-prodgate-pareto.rs`，展示了硬约束先行、多跳局部束搜索、去重和 Pareto 输出。
2. 五条 21×26 生产分支共同包含的 `592d836`
   - 展示固定辅键和声母/声介头部关系怎样在 proposal 层提前拒绝，不把无效候选送进求分器。

`11713b6` 的搜索器不能直接 cherry-pick：它写死旧的 `27 heads + 35 finals` 拓扑和当时机器的任务输入。应复用其搜索结构，把状态和约束换成“11 韵固定、少量声介原子例外”。

## 本轮完成的 Rust 边界

`SchemeState` 现在可以通过 `from_toned_codes` 接收 `pinyin × 5 tones` 的直接二键码表，并明确使用 `toneKeysByTone` 命名。旧的无调 `RegularLayout` 路径保持不变。

直接带调状态已经支持：

- 按语料词条的实际声调选取二键码；
- 修改某个拼音的某一调二键码；
- 通过已有 `by_pinyin` 倒排依赖找出需要重建的行；
- 继续使用已有的精确碰撞连通分量更新、摘要增量和回滚。

当前依赖粒度是“拼音”，不是“拼音×调”，所以它可能多重建同一拼音的其他调，但不会漏行，也不会改变结果。等准确流水线跑通后，再根据实测热点决定是否细化为五调倒排。

新增单测覆盖带调取码、变更和增量依赖；全 crate 回归通过。

## 仍需补齐的 CKT v5.1 适配

旧 `NativeCorpus` 的三字词只保存两个辅助位置；本研究固定的 v5.1 `word3=213` 则需要：

```text
AAA → AAAB → AAABB → AAABBB
```

也就是三次辅助追加。字符、二字词和四字词的现有数据结构更接近目标，但仍应由同一导出器生成，避免 JS/Rust 语料过滤差异。

最小而稳妥的实现顺序是：

1. 从当前 JS scorer 导出紧凑的 v5.1 固定策略模板，保留字符、二字、三字、四字四条 track 的权重和全部 stage；
2. Rust 读取模板，并用直接带调状态重建受影响行；
3. 用基线、单一声介例外和随机小邻域做逐 track 数值对拍；
4. 对拍通过后再接搜索器和断点续跑，不先做长期退火。

## 状态、约束与 Pareto 口径

搜索状态不应再用通用的 27/35 任意交换，而应由以下部分组成：

- 固定的 11 韵和三横 `7:7:7` 第二码表；
- 固定低碎片声介骨架；
- 一个很短的声介例外列表；
- 每个例外是不可拆的声介原子，不允许同一声介飞到多个第一码键；
- proposal 只做单原子移动、两原子交换，以及少量有规则含义的整体桶移动。

每个 proposal 在求分前重算并限制：

- `M`：规则基线之外必须记忆的声介例外数；
- `D`：18 个传统书写声母在第一码关系上的位移；
- `F`：声母到第一码键关系的额外碎片数，继续沿用当前研究的关系计数口径；
- 可选诊断：桶占用、左右手、同指和运动代理，但不混进 M/D/F 定义。

前沿以 `(CKT v5.1, M, D, F)` 保存原始值，硬门槛先拒绝明显过乱的候选。第一批建议只放开 `ΔM=0..4`、很小的 `ΔD/ΔF`，观察每增加一条例外能换回多少 CKT，再决定是否扩大。

## 速度判断

当前 JS 完整 scorer 对一个固定策略候选的实测为 **12.47 秒**。它每次从头构造并消解四条 track，适合最后复核，不适合数万次小邻域 proposal。

现有通用 Rust 退火器在一次烟测中，20 个大范围 27/35 proposal 全部越过增量阈值而退化为全量更新，约为 **1.7 秒/候选**。这个数字不能代表目标搜索：少量声介原子移动只会改变一小组拼音，正是倒排依赖和碰撞连通分量增量更新能够获益的情形。

因此当前工程判断是：

- 只复算几十个 finalist：继续用 JS 即可；
- 搜索几千到数万次少量声介例外：Rust 很可能有数量级价值；
- 在 v5.1 模板对拍完成前，不用不等价的旧 Rust 分数启动长期任务。

## 下一步

下一实现点是“固定 `12/213/24` 的 v5.1 紧凑模板导出＋Rust 读取和 JS 对拍”。通过后，把 `11713b6` 的受控邻域/Pareto 结构改造成专用声介例外 runner，再做短基准决定长期预算。四调任意染色和韵侧继续扩张都不进入该 runner。
