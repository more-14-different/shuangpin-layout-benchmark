# 带调 21×21 声介例外 Rust core 试跑

日期：2026-11-10

## 范围

本轮只验证三件事：Rust 与 JS 的 CKT v5.1 数值是否同口径、短程增量搜索的吞吐和资源占用是否适合转移到另一台 PC、少量声介例外是否有可见下潜空间。没有在本机启动长程退火，也没有扩大四调染色、韵分组、120 种形笔语义或 144 套词辅空间。

固定合同为拼读 11 韵、三横 `7:7:7`、`shapeKeysByMeaning=QAOPL`、词辅 `12/213/24`。基线为 `LOWMD-pindu11-499309-C0412356`，保守 `M_guard=26`、`D=11`、`F=9`。

## 数值对拍

Rust v5.1 适配补齐了三字词的四阶段：

```text
AAA → AAAB → AAABB → AAABBB
```

并给 CKT 摘要增加第三辅键的 300 ms 认知成本和 v5.1 的 6 候选翻页口径。289,644 行完整基线得到：

| 实现 | CKT v5.1 |
|---|---:|
| JS 原 scorer | 9.55914155647448 |
| Rust | 9.559141556474 |

D/F 也复现为 `11/9`。另对 3 个增量候选逐一执行 Rust 全量重算校验，均与增量结果一致。

## 性能与资源

纯增量前 100 个候选实测：

| 指标 | 数值 |
|---|---:|
| 增量候选吞吐 | 0.952 候选/秒 |
| 当前 JS 完整评分 | 约 12.47 秒/候选 |
| 相对 JS 加速 | 约 11.9 倍 |
| 峰值工作集 | 369.1 MiB |
| 峰值私有内存 | 384.4 MiB |
| 紧凑语料文件 | 5.60 MB |
| 100 候选检查点 | 40.8 KB |

扩展到 120 个候选并两次断点续跑后，累计纯搜索时间 119.443 秒，约 1.005 候选/秒。断点从 100 继续到 110、再到 120，结果和顺序稳定；`duty-ms=5` 节流正常。

增量规模没有很小：平均直接重建 21,588.5 行，平均精确碰撞闭包 50,259.3 行，最大分别为 46,157 和 96,771 行；总语料为 289,644 行。因此当前 core 已足够把数千至数万候选移交另一台 PC，但不应期待百倍加速。长期机可以用 `duty-ms` 控制占用，并按固定间隔写小型 JSON 检查点。

## 初探下潜空间

试跑只覆盖确定性一跳队列的前 120/1,100 个候选：完整覆盖零声母 `_/_i/_u/_v`、`b`、`bi` 六个声介原子的 20 个目的键。不是一跳全空间证明，更不是二跳或退火下界。

当前最佳是把声介原子 `bi` 从 H 键单独移到 M 键：

| 方案 | CKT v5.1 | M_guard | D | F |
|---|---:|---:|---:|---:|
| 基线 | 9.559141556 | 26 | 11 | 9 |
| `bi → M` | **9.531242744** | 27 | 11 | 9 |
| `bi → Y` | 9.547547407 | 27 | 11 | 9 |
| `bi → W` | 9.550448911 | 27 | 11 | 9 |
| `bi → B` | 9.572878471 | 27 | **10** | **8** |

`bi → M` 比基线改善 **0.027898812**，并比历史 M21 `qaopl_quality_original=9.541521260` 低 **0.010278516**，代价是当前保守口径多一条声介例外。原 JS scorer 独立完整复算为 `9.531242744125908`，与 Rust 的 `9.531242744125848` 一致。

这个结果证明“固定 11 韵＋7:7:7，只放少量声介原子例外”确实存在有意义的下潜空间。当前证据还不足以判断 `M_guard=27` 是否形成生产甜点，也不能把前 120 个候选冠军当成一跳全局冠军。

## 转移到长期机的建议

1. 先完整跑完 1,100 个一跳候选；这台机器的实测预计约 18–20 分钟。
2. 从一跳 `CKT/M/D/F` Pareto 选很小的 beam，再跑二跳；不要直接开放任意 55 原子退火。
3. 保持 300–500 MiB/进程预算。若并行多链，按内存而不是逻辑核数定进程数。
   本机全套 Rust 测试的默认并行编译曾碰到 Windows 页面文件上限；改为 `CARGO_BUILD_JOBS=1` 后全套通过，因此复算 recipe 已固定串行编译。
4. 保留 `duty-ms=5`、每 100 候选检查点、每 250 候选一次全量一致性验证；最终候选仍用 JS scorer 复核。
5. 若长程规模超过数万候选，再优化“候选后回滚到基线”的双次闭包成本；本轮无需为 18–20 分钟的一跳任务先重写 resolver。
