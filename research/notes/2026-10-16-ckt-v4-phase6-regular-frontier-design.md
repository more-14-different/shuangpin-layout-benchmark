# CKT v4 第 6 阶段：规则拓扑广覆盖与前沿搜索设计

状态：设计待复核。本文是第 6 阶段的范围和验收规格，不代表实现已经完成。

## 目标

第 6 阶段继续以 CKT v4 为退火的唯一主目标，在现有 Rust CPU 参考内核上扩大**规则拓扑方案**的有效搜索邻域，并输出可审计的方案能力、人体工学诊断和多目标前沿。它服务于 HTML 中现有及后续加入的同类方案，不能把某个代表方案的 ID、尺寸或键位写成通用规则。

这里的规则拓扑沿用阶段 4—5 的定义：每个计分音节由 27 个声母状态和 35 个韵母状态中的一对生成，状态再映射到 34 键全集 `ABCDEFGHIJKLMNOPQRSTUVWXYZ[]\\;',./`。零声母在种子中已经形成的等价组保持原子性；不同零声母结构族使用不同种子开链。

成功标准如下：

1. 严格唯一域不再因为单组移动几乎总是非法而失去换组能力；
2. 所有 HTML 方案均获得机器可读的正向评分/规则退火能力判定和原因；
3. 任一被标为可退火的种子都能由规则状态重建全部 CKT v4 计分音节，并保持尺寸约束；
4. CKT v4、M/D/V、MX 和负载的角色分离，不用未声明的混合总分偏袒某个尺寸；
5. 长跑继续满足低内存、低占用、可恢复和确定性审计要求。

## 明确不做

本阶段不为 `N095`、`H37` 或其他特殊拓扑编写专用退火适配器，也不从最终码表猜测它们的规则。已确认的两个代表情况是：

- `N095` 使用还原式韵母分支，例如 `a / ia / ua` 属于不同规则槽；
- `H37` 使用书写式韵母分支，例如 `ju/qu/xu/yu` 与 `lv/nv` 的次键规则不同。

二者仍参加完整 421 项码表的 CKT v4 正向评分，但标记为“特殊拓扑，阶段 6 不参与退火”。该标记按能力检查得出，而不是把 `23×23`、`25×30` 或某两个 ID 整体列入黑名单；同尺寸的其他方案只要通过规则往返就可以参加。

本阶段也不实现 GPU 后端、不允许任意逐音节改码、不改变 CKT v4 公式、不宣称找到全局最优解。

## 能力判定

能力审计为每个方案分别报告：

- `forwardScore`：完整码表能否生成并计算 CKT v4；
- `regularAnneal`：是否能进入 27+35 规则状态退火；
- `contract`：21×21 的 `aaa` 独立三字词合约，或其他尺寸的 `aaau` 联合池合约；
- `common399Policy`：允许碰撞或必须唯一；
- `reasonCode` 与说明：不支持时给出第一个稳定、可测试的失败原因。

`regularAnneal` 必须同时满足：

1. Common399 中每个音节都有合法双键码；
2. 同一声母状态的首键一致，同一韵母状态的次键一致；
3. 由规则状态重建后，Common399 逐项等于原方案；
4. 实际声母/韵母用键数等于声明容量；
5. 辅码互斥和分尺寸 Common399 规则通过现有严格验证。

扩展 22 音节不进入冻结的 CKT v4 语料，因此其差异不能悄悄改变分数；能力报告仍应单独记录扩展表是否也完全往返。显式请求退火一个不支持的方案时必须失败并报告原因；批量审计则跳过并保留记录，不能静默退化为逐音节自由状态。

## 严格唯一域的复合邻域

阶段 5 的单声母组移动会暂时减少已用键数，并常在 21×26 等严格唯一域立即失败。第 6 阶段增加保持容量的原子复合提案：

1. **成对重分组**：从两个键各选择一个原子组并同时迁移，使两个源键仍非空，或让一个组占用对方腾出的键；
2. **三环重分组**：三个不同键上的原子组按一个方向循环，改变组成员关系而不是只交换整键标签；
3. **韵母成对/三环移动**：与声母相同，但单个韵母就是最小原子；
4. **合法性引导修复**：先提出一次组移动，再只枚举能够恢复容量的第二步或第三步，完整候选通过 Common399 唯一性后才进入评分。

现有整键换位继续保留，因为它探索的是物理键位置；复合重分组探索的是组成员关系，两者不能互相替代。零声母等价组不得在复合提案中被拆开。

提案生成必须先满足便宜的结构约束，再运行 Common399 唯一性检查，最后才生成约 29 万行的联合池差分。固定随机种子下，提案类型、候选和接受结果必须可复现。检查点记录每类提案的提出、结构拒绝、唯一性拒绝、评分和接受次数，避免只看总接受率。

## 指标、护栏和 Pareto 结果

CKT v4 仍是模拟退火接受概率中的唯一能量。其他指标分为两类：

- M/D/V、MX、手指/键位负载可以成为显式命令行硬护栏；
- 未设为护栏时，它们只作为诊断和 Pareto 维度输出，不回写 CKT v4。

每次运行必须把启用的护栏及其阈值写入检查点和结果。不同护栏配置的冠军不能伪装成同一搜索口径。

在线长跑不在内存中保存所有候选。它只保留当前状态、最低 CKT 状态、有限的诊断领导者和可恢复检查点；符合记录条件的候选以追加式紧凑记录写盘。运行结束或按周期执行离线精确 Pareto 归并，使用完整未舍入值支配判断，再生成便于阅读的汇总。展示时的舍入值不得参与支配关系。

首版前沿至少包含：CKT v4、M、D、V；MX 与负载只有在按冻结历史定义完成逐项复现后才加入正式前沿。在复现完成前可以输出实验字段，但必须标记 `provisional`，不得用于淘汰候选。

## 数据流和组件边界

1. JS 导出器读取 HTML 全方案，保留完整正向评分状态，并生成能力审计所需的来源信息；
2. Rust 能力审计器尝试规则编译、Common399 往返和严格验证，输出逐方案记录；
3. Rust 提案器只接收已经通过能力审计的 `RegularLayout`；
4. 候选通过结构与唯一性验证后，沿用阶段 5 的增量/全量自动选择进行 CKT v4 精确评分；
5. 接受状态写入检查点，满足记录条件的状态写入追加日志；
6. 独立归并器从日志重建并验证 Pareto 前沿，最终候选再做一次全量 CKT v4 复算。

能力审计、提案生成、评分和前沿归并必须保持独立接口。正向评分支持不意味着退火支持；前沿归并失败也不能破坏已写入的退火检查点。

## 错误处理与低负载约束

- 单方案命令遇到不支持拓扑时返回非零退出码和结构化原因；
- 全方案能力审计不因一个不支持方案中止；解析或数据损坏仍视为整体失败；
- 恢复时校验语料哈希、方案、提案策略、护栏、目标步数和格式版本；
- 追加日志使用稳定状态摘要去重，尾部不完整记录在恢复时忽略并报告；
- 默认单线程，保留 `--duty-ms` 主动让时；多进程和 GPU 都不是本阶段默认行为；
- 不把全部方案、全部候选或完整联合池副本同时常驻内存。

## 验证与验收

实现必须按测试先行完成以下证据：

1. 成对和三环提案的单元测试先证明旧实现缺少合法路径，再证明新候选保持容量、辅码约束和零声母原子性；
2. 21×26、21×28 以及至少一个其他可重建尺寸完成严格 Common399 唯一性测试；
3. 21×21 和可重建的 23×23 仍只按尺寸规则允许碰撞，不因本阶段修改而被误设为唯一；
4. 对 HTML 全方案生成稳定能力报告；`N095`、`H37` 的正向评分为支持、规则退火为不支持且原因明确；
5. 所有支持方案的 Common399 规则往返逐项相同，Rust 与 JS 的 CKT v4 四轨结果继续一致；
6. 固定种子连续运行与中断恢复产生相同最终状态、前沿成员和计数器；
7. Pareto 归并使用原始数值，拒绝被任一现有成员完全支配的候选，并正确移除被新候选支配的旧成员；
8. 低内存冒烟测试证明候选数量增长不会导致常驻内存随历史线性增长；
9. Rust 格式、Clippy、单元/集成测试及 JS 回归测试全部通过。

## 实施顺序

1. 全方案规则能力审计和结构化原因；
2. 声母、韵母的成对与三环复合提案；
3. 分类型提案统计、确定性恢复和多尺寸端到端审计；
4. 追加式候选记录与离线精确 Pareto 归并；
5. 冻结 MX/负载来源并逐项复现，随后接入可选护栏和正式前沿；
6. 在 research notes 中记录能力矩阵、实验口径、失败范围和目标台式机 CPU 基线。

只有这些 CPU 路径在 JS 参考、恢复确定性和长时间低负载上稳定后，才另行设计可选 GPU 批量后端。
