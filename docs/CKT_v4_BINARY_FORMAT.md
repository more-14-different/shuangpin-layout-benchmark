# CKT v4 紧凑行格式

状态：阶段 2 的第一版真实语料交换格式。它用于 JS 权威适配器与 Rust CPU 参考内核之间的可审计交接，不是最终退火状态格式。

## 目标与边界

旧真实验证夹具把约 29 万行/模式全部写成 JSON；S005 与 L600 四个块共 271.7 MiB，Rust 还会一次反序列化全部块。紧凑格式改为：

- JS 从冰雪词典和 HTML 直接写二进制，不产生巨型 JSON 中间件；
- 文件保存短 JSON 元数据头，行体使用定宽整数、`f64` 和长度前缀字符串；
- Rust 一次只读一个“方案×模式”块，评分、核验并释放；
- 省略评分不使用的词条正文，但保留稳定 ID、权重、全部阶段码和 JS 预期四轨；
- 34 键索引为 `ABCDEFGHIJKLMNOPQRSTUVWXYZ[]\;',./`，每键 6 bit，1–6 键码装入 `u64`。

该文件仍保存每个方案生成后的完整阶段行，因此它解决跨语言验证的空间峰值，不等同于退火所需的“共享语料基底 + 方案状态 + 受键交换影响的倒排表”。后者是阶段 2 的下一里程碑。

## 文件结构（little-endian）

文件头：

| 字段 | 类型 | 含义 |
|---|---:|---|
| magic | 8 bytes | ASCII `CKTV4ROW` |
| format version | `u16` | 当前为 `1` |
| flags | `u16` | 当前必须为 `0` |
| metadata length | `u32` | UTF-8 JSON 字节数，最大 1 MiB |
| metadata | bytes | 下述审计元数据 |

元数据声明格式版本、导出器、34 键字母表、全部认知参数、扩展键 donor/距离守卫、词库质量与各词长数量、块数，以及 HTML、冰雪主词典、笔画词典、上游运动快照的 SHA-256。SHA-256 用来锁定来源；当前 v1 尚未附加整个二进制载荷的内容校验和。

每个方案/模式块：

1. `u16 + UTF-8` 方案 ID；
2. 两个 `u8` 键盘口径；
3. `u8` 合约：`0` 为传统 21×21，`1` 为四码顶；
4. `u8` 模式：`0` 为键道，`1` 为三拼；
5. `u32` 行数；
6. 按单字、二字词、三字词、四字词顺序的四条预期汇总轨：`u32 count` 加九个 `f64`；
7. 顺序行体；
8. `u32 0xC4E0CA5E` 块尾标记。

每行保存 `u32 + UTF-8` 稳定 ID、`u8` 词长类型、`f64` 权重、`u8` 基础码长、`u8` 阶段数。每阶段保存 `u8` 终止码长、`u8` 候选池编号、`u16` 候选码数，随后是相应数量的 `u64` 打包码。码长由阶段给出，不在每个候选码上重复。

候选池编号按以下固定顺序：

```text
0 char:base       1 char:aux1       2 char:aux2
3 word:four       4 word:five       5 word:six
6 word3:three     7 word3:four-b    8 word3:five-bb
```

所有枚举编号和排序都是格式合约，不能随 Rust 枚举声明顺序隐式变化。

## 复现与验证

```powershell
just ckt-v4-binary-fixture "S005,L600"
just ckt-v4-binary-verify
just ckt-v4-binary-incremental-smoke
```

2026-10-16 本机实测：四个真实块从 JSON 的 271.7 MiB 降至 68.6 MiB；Rust release 纯读取与全量评分约 3.5 秒，25 ms 采样峰值工作集约 136 MiB。四块的四轨全部字段均与 JS 一致；增量换位、全量复核、回滚再次复核也全部一致。测量仅用于同机阶段比较，不外推为目标台式机性能。
